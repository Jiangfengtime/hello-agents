## 1. 为什么不能直接在根目录“运行整个项目”

本仓库同时包含教学脚本、Notebook、平台导出配置、Vue Web 应用、Godot 项目和社区案例。它们没有统一的入口、依赖版本和生命周期。

正确的第一步是确定运行单元。例如第四章模型客户端、旅行助手后端、研究前端都可以独立启动。根目录是课程组织边界，不是单个服务的运行边界。

## 2. 解释器、包与源码的关系

### 2.1 解释器决定加载哪个环境

`python` 是终端解析到的命令，PyCharm 则可能选择另一个虚拟环境。系统中安装了某个包，不代表 IDE 使用的环境也有。

先在实际运行环境执行：

```bash
python -c 'import sys; print(sys.executable); print(sys.version)'
python -m pip --version
python -m pip show hello-agents
```

`python -m pip` 让 pip 跟随当前解释器，比单独使用另一个可能指向不同环境的 pip 命令更明确。

### 2.2 导入名与发行包名不同

安装名是 hello-agents，导入名是 hello_agents。查看实际源码位置：

```bash
python -c 'import hello_agents; print(hello_agents.__file__)'
```

如果它位于 site-packages，就需要在那里继续查看框架内部实现。不要在当前教程仓库中无限寻找不存在的同名框架目录。

### 2.3 签名和返回类型怎样核对

在包可正常导入时，可用 inspect 查看：

```python
import inspect
from hello_agents import HelloAgentsLLM

print(inspect.signature(HelloAgentsLLM))
print(inspect.signature(HelloAgentsLLM.invoke))
print(inspect.getfile(HelloAgentsLLM))
```

签名帮助判断参数名是否匹配；返回类型还要结合方法实现或一次受控调用确认。注解不是运行结果的替代证据。

## 3. 按案例隔离依赖

第七章正文、评估章节和三个应用使用的框架版本存在跨度。分别创建环境可以避免为某应用升级后破坏另一个教学示例。

本项目总览已列出各处版本声明。实际准备时先查看当前案例的 requirements/pyproject/lock 文件，再安装，不要直接认为 README 中提到的新框架版本适配全部历史代码。

已有 lock 文件时，它提供更具体的依赖解析信息；requirements 中的范围则可能在不同时间解析出不同组合。是否成功安装还要检查当前 Python 版本与系统条件。

## 4. `.env` 为什么写了却没有生效

### 4.1 `.env` 是文件，不会天然进入每个进程

程序需要通过 dotenv、配置库、启动参数或其他机制加载它。不同案例做法不同：第四章调用 load_dotenv；小镇 config 指定后端目录的 .env；研究 Configuration.from_env 读取 os.environ，文件加载要由启动方式负责。

### 4.2 工作目录决定部分路径含义

`./notes`、`./knowledge_base` 等相对路径通常以进程工作目录为起点，不一定以源文件所在目录为起点。

PyCharm 的 Working directory、终端当前目录和 uvicorn 启动目录不同，可能导致笔记“找不到”或生成到意料之外的位置。

### 4.3 配置优先级要看赋值表达式

常见形式是显式参数优先，再取环境变量，最后默认值；但本项目并非所有分支都相同。

第四章读取 LLM_MODEL_ID/LLM_API_KEY/LLM_BASE_URL；第七章 ModelScope 自定义分支使用 MODELSCOPE_API_KEY；CAMEL 示例读取 LLM_MODEL；第一章 `.py` 示例还会直接覆盖 Tavily 环境变量，而当前 Notebook 使用 `load_dotenv()` 后读取环境变量，两者应分别核对。

所以排查时要找到真正执行的分支，而不是把某个章节的配置表照搬到整个仓库。

### 4.4 安全地检查配置存在性

可以检查变量是否已设置，避免把真实密钥输出到日志：

```python
import os

print("LLM_MODEL_ID:", os.getenv("LLM_MODEL_ID"))
print("LLM_API_KEY configured:", bool(os.getenv("LLM_API_KEY")))
```

这只确认当前进程环境，不证明后续 provider 一定读取这个字段。最终以客户端初始化结果为准。

## 5. 一条请求的调试顺序

```text
解释器 → 导入 → 配置 → 模型连接 → 工具独立执行
→ Agent 控制循环 → API → 页面
```

每一步解决一个问题。模型地址错误时先调整提示词没有意义；前端跨域错误时，也不应先修改 ReAct 正则。

### 5.1 导入层

检查包是否存在、版本是否匹配、启动目录是否满足平级导入。研究后端使用 `from config import ...` 等写法，需要注意 src 的导入路径。

### 5.2 连接层

区分地址解析、连接失败、TLS、服务不可达、鉴权和请求 schema。完整 traceback 的最内层异常和 HTTP 响应通常比外层“Agent 执行失败”更有用。

### 5.3 业务工具层

独立调用天气、搜索、文件读取或 MCP 工具，确认参数、返回格式和凭证。能连接服务器和能完成工具操作是不同检查。

### 5.4 控制循环层

观察模型原文、解析动作、实际参数、Observation 与下一轮输入。若某一步数据丢失，模型可能重复调用或错误结束。

### 5.5 接口与页面层

核对路由前缀、请求字段、CORS、客户端超时和结果存储。页面没有显示不代表后端没有返回，页面显示结果也不代表真实工具已成功。

### 5.6 Notebook 与依赖安装如何逐层验证

在出错的 Notebook 内核中检查，而不是只看终端默认 Python：

```python
import sys
import importlib.util
print(sys.executable)
for name in ("requests", "tavily", "openai"):
    print(name, importlib.util.find_spec(name) is not None)
```

`find_spec` 只说明能找到模块，不代表所有依赖都能成功导入。安装发行包 `tavily-python` 后，再运行 `from tavily import TavilyClient` 验证导入。Notebook 可使用 `%pip install tavily-python`，它面向当前内核环境；若安装后内核仍持有旧模块，重启内核再按顺序运行配置单元格。

| 最先出现的错误 | 优先核查 | 不应直接得出的结论 |
| --- | --- | --- |
| `SSLEOFError` / TLS EOF | 网络、代理或 TLS 连接中断；比较切换网络后的结果 | 一定是包不存在或一定是证书过期 |
| 索引访问失败后 `No matching distribution` | 先恢复索引访问，再判断版本和 Python 兼容性 | 仅凭末行就判定包名无效 |
| `ModuleNotFoundError` | 当前内核解释器和模块导入名 | 系统中任何 Python 安装成功就够了 |
| LLM HTTP 404 | 服务商要求的 base URL、端点路径、模型名称/路由 | 首先修改 Thought/Action 提示词 |
| Action 解析失败 | 模型是否真的返回了成功响应，返回结构是否符合解析器 | 所有问题都来自模型不遵守格式 |

TLS 的 EOF 表示连接意外结束，不能仅凭它确定根因。关闭证书验证不能修复所有 TLS 问题，也会掩盖安全校验。遇到 404 等配置错误应先修配置；重试主要用于可恢复的瞬时失败，并结合超时和调用副作用决定策略。[Requests 对 HTTP 状态检查的说明](https://requests.readthedocs.io/en/latest/user/quickstart/#response-status-codes)

## 6. 核心断点清单

| 场景 | 断点 | 要确认的内容 |
| --- | --- | --- |
| 模型调用 | 调用前与响应后 | 实际 messages、model、响应类型 |
| ReAct | `_parse_output()` 后 | action 是否符合格式 |
| 工具调用 | 执行函数前后 | 参数值与实际返回 |
| 记忆 | 写入、检索、组装三处 | 内容是否完整传递 |
| 旅行规划 | 各专家返回、JSON 解析、fallback | 资料是否真实，是否回退 |
| 深度研究 | 线程启动、队列写读、任务状态 | 哪个任务产生哪条事件 |
| 小镇 | 增强消息、好感度更新、记忆保存 | 状态何时读写及所属玩家 |

## 7. 状态边界：统一用五类来分析

### 7.1 局部变量

一次函数调用内部存在，例如 Plan-and-Solve 的 history。函数返回后，不应假设其他请求还能访问它。

### 7.2 对象状态

保存在 self 上，例如 Agent._history。只要对象被复用，状态就可能继续存在；对象销毁则可能丢失。

### 7.3 模块级共享状态

全局规划器、全局模型实例、NPC 管理器会被同一进程的请求复用。多个请求共用对象时，要核对用户隔离与并发行为。

### 7.4 外部持久化

文件、SQLite、向量库和笔记目录可以跨对象或进程保留，但是否持久化、何时落盘、如何加载仍需看具体实现。

例如小镇的记忆路径与好感度字典是两类状态，不能因为其中一个有磁盘目录就推断另一个也会恢复。

### 7.5 客户端状态

旅行助手 sessionStorage 位于浏览器；Vue 内存状态位于页面；Godot 角色状态位于游戏进程。后端重启、页面刷新、关闭标签页和退出游戏，会分别影响不同状态。

## 8. 同步、流式与后台执行不要混为一谈

| 概念 | 表示什么 | 本仓库中的例子 |
| --- | --- | --- |
| HTTP 等待结果 | 请求保持到返回 | 旅行规划 JSON 接口 |
| 模型流式读取 | SDK 分段收到模型内容 | 第四章 think 内部处理分片 |
| Python 生成器 | 调用方迭代时推进方法体 | MySimpleAgent.stream_run |
| SSE 事件 | HTTP 持续发送结构化事件 | 深度研究流式接口 |
| 工作线程 | 多个任务在不同线程执行 | 深度研究 run_stream |
| 后台周期任务 | 定时更新状态 | 小镇 NPCStateManager |

async 函数可以包含同步阻塞调用，生成器也可能在未迭代时什么都不做。判断并发与执行时机，需要看实际调用位置。

## 9. 结果验证分为四层

1. 传输完成：请求得到响应，或事件流结束。
2. 结构有效：响应能通过 JSON/Pydantic 或页面解析。
3. 执行真实：相关模型与工具确实按预期运行。
4. 任务正确：输出解决了用户问题，且关键结论有依据。

旅行备用行程主要保证结构，小镇模拟回复保证基础交互，研究 done 表示流结束。它们都不能单独证明第四层成立。

## 10. 按主线学习的具体做法

### 10.1 第一轮：看懂最短闭环

读第四章 llm_client、tools、ReAct。画出一次请求的数据流，把模型文本与 Python 函数执行分开。

### 10.2 第二轮：理解抽象与状态

读第七章的模型、SimpleAgent 和 ReAct 扩展。比较 run/stream_run，标注 self、局部变量和全局对象的生命周期。

### 10.3 第三轮：理解信息怎样进入回答

读第八章记忆操作与 RAG search，再读第九章 build。用一个问题追踪资料从保存到检索再到 messages 的路径。

### 10.4 第四轮：追踪完整应用

先读旅行助手的一次表单请求，再读研究的一个任务事件生命周期，最后读小镇的一轮聊天和一次状态更新。

### 10.5 第五轮：验证与改进

使用固定样例评估一个明确问题。先找到失败发生在哪层，再改变一个因素，重跑相同输入。训练、换框架和增加 Agent 都应由具体缺口驱动。

# ReAct、Function Calling 与 Agent Loop：关系、差异和代码对应

[返回阅读导航](README.md) · [构建智能体与框架](02-构建智能体与框架详解.md)

本文整理围绕第四章示例的讨论，区分四件容易混在一起的事：整体循环、任务方法、工具调用机制，以及退出循环的条件。先理解它们的职责，再比较文本 `Action` 与结构化 `tool_calls`。

## 1. 先分清四个层次

| 概念 | 主要回答的问题 | 例子 |
| --- | --- | --- |
| Agent Loop | 智能体怎样接收信息、行动、接收反馈并继续？ | 感知 → 决策 → 执行 → 环境反馈 → 下一轮 |
| ReAct | 怎样让推理和行动相互配合，逐步解决任务？ | 先查天气，依据下雨改查室内场馆，发现闭馆再调整 |
| Function Calling | 模型怎样向程序提出函数调用请求？ | 请求 `Search`，参数为 `{"query":"北京天气"}` |
| 停止条件 | 程序何时退出？ | 输出 Finish、正常回答不含工具请求、达到轮数上限 |

这四个层次可以配合。修改其中一层，不一定需要把其余三层同时替换。

## 2. Agent Loop：整体运行机制

完整闭环可以写成：

```text
收到用户问题或环境信息
          ↓
感知、整理当前状态
          ↓
决定下一步行动
          ↓
程序执行动作，环境返回结果
          ↓
把结果作为新观察，再决定继续或结束
```

“感知 → 思考 → 执行”和“思考 → 行动 → 观察”并不天然冲突，它们可能从不同位置描述同一个闭环。工具执行后的反馈，是下一轮决策的输入；“观察”和“下一轮感知”往往有重叠，不必增加一次独立工具调用。

环境反馈属于完整交互闭环，环境本身通常画在 Agent 本体之外。请求超时、检索为空、场馆关闭，也都是反馈。

`while True`、有限步数的 `while` 或图状态机，都是实现循环的代码形式。仅看到循环语句，不能判断它采用的是 ReAct、固定工作流还是其他任务方法。

## 3. ReAct：推理和行动怎样相互配合

ReAct 是 Reasoning 与 Acting 的结合。原论文研究交替生成推理轨迹和任务动作：推理帮助制定、追踪、更新计划和处理异常；行动使模型能够从外部环境获取新信息。这一方法既可通过提示示例引导，也可使用相关轨迹训练。[ReAct 原论文项目页](https://react-lm.github.io/)

例如用户要求：“查询北京天气，再推荐一个合适的景点。”

| 阶段 | 教学示意 |
| --- | --- |
| 判断 | 推荐景点之前，先确定天气。 |
| 行动 | 查询北京天气。 |
| 观察 | 返回下雨。 |
| 更新判断 | 优先考虑室内，而且需要确认开放信息。 |
| 行动 | 查询室内场馆及开放情况。 |
| 观察 | 候选场馆今天闭馆。 |
| 再次更新判断 | 当前候选不适用，需要找其他场馆。 |
| 行动与观察 | 查询替代场馆，得到符合条件的结果。 |
| 回答 | 综合天气和开放信息给出推荐。 |

关键是**推理指导行动，行动反馈又改变后续判断**。不是提前生成一串搜索词并机械执行，也不是让模型把未来工具结果编写出来。

经典教学形式常写作 `Thought → Action → Observation`。但 ReAct 不要求每次行动前都打印等长的推理文字；原论文也讨论了稀疏推理轨迹。展示一段 `Thought` 同样不能证明答案正确，也不能把模型生成的文字当成对其内部计算的完整解释。

## 4. Function Calling：表达调用请求的机制

Function Calling 让模型根据工具定义，生成函数名称和参数。应用程序仍负责校验、选择注册函数、执行以及回传结果。

以项目使用的 Chat Completions 兼容接口为例，请求中的 `tools` 告诉模型有哪些工具；响应中的 `tool_calls` 表示模型这一次具体要求调用什么。两者名称相近，但方向和含义不同。[OpenAI Docs：Function Calling](https://developers.openai.com/api/docs/guides/function-calling)

```text
程序 → 模型：tools = 可用工具清单及参数定义
模型 → 程序：tool_calls = 本轮具体调用请求
程序 → 工具：执行真实函数
程序 → 模型：回传真实执行结果
```

例如响应的一部分可以简化为：

```json
{
  "content": null,
  "tool_calls": [
    {
      "id": "call_1",
      "type": "function",
      "function": {
        "name": "Search",
        "arguments": "{\"query\":\"北京天气\"}"
      }
    }
  ]
}
```

注意，`arguments` 在这个接口中仍是 JSON 编码的字符串，需要程序解码和校验。结构化字段减少了从自由文本提取动作的工作，并不自动保证工具名、参数或事实正确。

Function Calling 本身没有规定完整任务必须怎样推进。它可以用于一次调用、多轮自主决策、固定工作流或多个 Agent 的协作。

## 5. 两者有什么关联，为什么不能直接等同

```text
ReAct 任务过程
  判断下一步
      ↓
  提出行动请求 ── 可以使用 Function Calling
      ↓
  程序执行，获得观察
      ↓
  根据观察更新判断
```

因此：

- ReAct 可以使用原生 Function Calling 来表达行动请求。
- ReAct 也可以使用文字 Action、命令协议或其他执行接口。
- 使用 Function Calling，不足以证明整个系统采用了 ReAct。

例如，模型只生成一次天气工具调用，程序随后按固定规则“下雨就推荐 A 场馆”完成响应，这展示了 Function Calling，却没有展示 ReAct 中由模型结合观察持续组织推理与行动的过程。

反过来，程序用正则解析 `Action: Search[...]`，再把真实结果交给模型，由模型不断更新判断，也可以实现 ReAct。**“正则还是结构化字段”是两种调用实现的差异，并不是 ReAct 与 Function Calling 的定义差异。**

如果某个原生工具循环确实组织了推理、行动与反馈的交替，可以称其采用 ReAct 思路。仅凭 `while True` 或出现 `tool_calls`，不能判断模型具体采用了什么推理策略。严格讨论原论文方法时，应进一步查看提示、训练轨迹和实际决策过程。

## 6. 原方法与新方法：实际改了哪些东西

本地两个入口分别是：

- [ReAct.py](../../code/chapter4/ReAct.py)：文字协议的教学版 ReAct。
- [ToolCallingAgent.py](../../code/chapter4/ToolCallingAgent.py)：使用原生工具请求的循环示例。

它们都让模型选择工具和参数，程序都执行注册的真实函数。具体实现差异如下：

| 环节 | 原 ReAct.py | 新 ToolCallingAgent.py |
| --- | --- | --- |
| 工具描述 | 拼进提示词 | 从原注册表生成请求的 `tools` 定义 |
| 模型的请求 | 文本 `Action: Search[...]` | 响应的 `tool_calls` 字段 |
| 参数解析 | 正则提取方括号内容 | 解析 `function.arguments` 的 JSON |
| 真实函数调用 | `tool_function(tool_input)` | 同样是 `tool_function(tool_input)` |
| 结果回填 | `Observation:` 历史文本 | 带 `tool_call_id` 的 `role="tool"` 消息 |
| 正常结束 | Action 以 `Finish` 开头 | 正常响应不再包含工具请求，并有回答文本 |
| 循环 | `while current_step < max_steps` | `while True`，内部保留同样的步数检查 |
| 推理呈现 | 提示词要求显式 Thought | 没有要求显式输出 Thought |

这里同时涉及**调用机制**和**停止条件**的变化。不能把所有差异都归结为 Finish，也不能据此说“旧的就是 ReAct，新的与 ReAct 完全无关”。

### 6.1 为什么新增 `_think()`

旧 [`llm_client.py`](../../code/chapter4/llm_client.py) 的 `think()` 只收集 `delta.content`，最后返回字符串，没有传 `tools`，也不返回 `delta.tool_calls`。如果模型只返回工具请求，调用方可能拿到空字符串。

新 `_think()` 复用旧对象的模型配置和底层客户端，补充工具定义，并在流式输出中按调用索引拼接工具名称和参数。工具请求完整以后，才交给循环执行。它的职责是取得完整的模型响应，不是额外的第二个“思考模型”。

这是在“不改现有代码”的约束下增加的新方法。如果允许扩展旧 `think()` 的请求参数和返回值，也可以复用扩展后的方法，但需要检查其他调用方对字符串返回值的依赖。

### 6.2 搜索函数实际上没有换

两个入口最终都从 `ToolExecutor` 中取出函数，再调用：

```python
tool_function = self.tool_executor.getTool(tool_name)
observation = tool_function(tool_input)
```

原 [`tools.py`](../../code/chapter4/tools.py) 的搜索服务、解析优先级和最多三条普通搜索摘要仍保持原行为。给模型换一种请求表达方式，不会自动增加网页正文抓取、来源核验或事实校验能力。

## 7. Finish 与没有工具请求：两个停止协议

原方式约定：模型明确输出 `Action: Finish[答案]`，程序进入返回分支。它检查的是解析出的 Action，不是回答的任何位置出现 Finish 就结束。

新方式约定：一次模型响应正常结束，不再要求调用工具，并且有有效回答文本，程序就返回。请求仍然可以带着 `tools` 清单；模型有工具可选，不意味着必须使用。

两者都表示模型选择了结束，但都不证明答案已正确完成任务。模型也可能直接承认信息不足、遗漏必要查询，或者给出缺少依据的回答。

需要区分三种状态：

| 状态 | 处理含义 |
| --- | --- |
| 模型按正常协议结束 | 返回回答，再按任务要求验收 |
| 轮数、时间或预算耗尽 | 强制停止，不冒充任务已完成 |
| 模型请求或协议异常 | 报错或进入恢复流程，不当作正常结束 |

### 7.1 可以只改结束条件，不换调用机制吗

可以。文字协议也能约定“有 Action 时执行，没有 Action 时直接回答”。但必须能区分正常回答、格式错误和请求失败，不能简单把“正则没匹配到”一律解释为成功。

原生工具接口也能额外定义一个名为 Finish 的终止函数，由程序将它识别为结束信号；那是应用自己的工具协议，不是接口强制提供的特殊能力。因此，停止协议与工具请求的表达机制可以分别选择。

### 7.2 `while True` 的作用是什么

它只改变循环的代码写法。继续还是退出，由分支中的 `return`、`break`、异常或预算判断决定。换成 `while True` 不会让模型更会规划，也不代表必须无限运行。

当前新示例保留默认 5 轮模型调用上限。一轮可能包含多个工具调用，最后一次生成回答也占一轮；达到上限时返回 `None`，不保证任务已经完成。

## 8. 如何判断日志中的“观察”是否真实

模型在普通回答里写出 `Observation: ...`，并不意味着程序执行过工具。真实观察必须来自程序实际调用及其返回值。

原文字解析示例中，一次模型输出若包含多个 Action、模拟 Observation 和 Finish，宽松正则可能将它们整段吞进搜索参数。原生工具字段能减少这种自由文本提取问题，但仍需校验调用参数和处理工具错误，也不能阻止模型在普通回答中生成不实陈述。

读日志时追踪“程序接收的调用 → 函数执行 → 实际结果 → 回填消息”，而不是仅数模型文本中出现了多少次 Action 或 Observation。

## 9. 自测

1. 模型通过 Function Calling 查询一次汇率，程序计算金额后直接返回，是否仅凭这一点就能认定是 ReAct？
2. 模型用文字 Action 请求搜索，根据返回的闭馆信息更换候选，是否一定需要原生 Function Calling？
3. 把 `while current_step < 5` 改成 `while True`，是否改变了任务方法？
4. 模型正常回答“证据不足，无法确认”，且没有工具调用，是否意味着原任务已经成功？

参考答案：1. 不能，只能确认使用了函数调用机制。2. 不需要，文字动作也能承载 ReAct。3. 不一定，只改变循环写法；仍需看内部决策逻辑。4. 它可以是一次正常结束，但不等于已经获得原任务要求的事实答案。

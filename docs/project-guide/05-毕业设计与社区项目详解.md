> 对应第十六章与 Co-creation-projects。章节要求依据本地文档；架构模板、开发步骤和验收案例是本文提供的实践建议，不表示仓库已实现新的业务项目。

## 1. 毕业设计要证明什么

前面章节分别展示模型、工具、记忆和协作，毕业设计需要证明你能围绕一个具体目标选择这些能力，并让输入、执行、结果和验证形成完整链路。

评判重点不是用了多少技术名词，而是：用户的问题是否清楚、结果是否有用、流程能否复现、错误能否解释、效果是否有证据。

[第十六章正文](../chapter16/第十六章%20毕业设计.md) 将成果放在社区共创目录，要求可运行的 Notebook 或 Python 脚本、依赖列表和 README，再通过开源协作提交。

## 2. 怎样选一个范围合适的题目

### 2.1 把“做一个万能助手”缩成可验收任务

一个可执行的题目至少写清以下内容：谁使用、输入是什么、要交付什么、为什么需要模型、什么情况算完成。

例如可以把“代码助手”缩为“输入一份 Python 文件，输出带源码位置和解释的审查报告”。这样就能明确读取范围、报告格式和验收样本。

如果目标仍是“自动解决所有编程问题”，工具边界、执行权限和成功条件都过于开放，难以定位失败。

### 2.2 什么时候需要 Agent

如果任务始终是“读取固定文件 → 用固定提示词总结”，一次模型调用或固定工作流可能足够。

如果模型需要根据中间结果决定继续查哪个文件、调用哪个工具、如何补充证据，就有更明确的 Agent 控制需求。

这种判断帮助你把复杂度放在真正需要的位置。多一步循环，就多了状态、终止和错误处理责任。

### 2.3 什么时候需要多个 Agent

多个角色适合具有明确分工、不同信息范围、不同工具权限或独立评价职责的任务。例如研究者收集资料，撰写者综合，评审者检查来源覆盖。

如果只是把同一问题交给多个相似提示词，没有清楚的输入输出契约，可能增加成本，却让结果更难追踪。

## 3. 从需求落到数据契约

以“源码阅读助手”为示意设计：

| 契约 | 建议内容 |
| --- | --- |
| 输入 | 项目路径、用户问题、允许读取范围 |
| 中间证据 | 文件路径、源码片段、符号名、观察结论 |
| 输出 | 架构解释、调用链、源码引用、未确定事项 |
| 结束 | 已回答问题，或明确说明缺少哪些材料 |
| 失败 | 路径不存在、文件不可读、预算用尽、模型调用失败 |

先定义这些数据，再设计 Agent 角色。否则常见结果是模型输出很多文字，但前端无法组织，评估器无法判定，后续工具也无法接收。

## 4. 建议的最小架构

以下目录是建议模板，不是强制要求：

```text
your-project/
├── main.py                 入口与参数解析
├── agents/                 执行策略和任务编排
├── tools/                  文件读取、查询等真实操作
├── models.py               输入、证据与输出数据结构
├── config.py               配置读取与校验
├── examples/               可复现样例
├── requirements.txt        依赖
├── .env.example            配置字段与占位值
└── README.md               运行、示例、边界与验证
```

入口负责接收参数，编排层决定顺序，工具负责执行，模型层统一数据形状。不要让一个超长 Prompt 同时替代所有这些职责。

## 5. 分阶段完成，而不是一次堆齐能力

### 5.1 阶段一：最小输入输出

先让程序接收一个真实输入，得到一个可检查结果。可以是命令行，不必立即实现 Web 页面。

这一阶段只需证明模型连接和最基本的数据流是通的。把实际模型标识、参数和输出保存下来，建立后续比较基线。

### 5.2 阶段二：接入一个真实工具

选择最关键的操作，例如读取文件或检索资料。把工具返回值做成清晰结构，并区分无结果、参数错误和执行失败。

先独立验证工具，再交给 Agent 选择调用。这样出现错误时，可以区分工具本身与模型调度。

### 5.3 阶段三：加入有限控制循环

设置最大步数或调用预算，明确完成信号，确保每次工具结果都回到下一轮输入。

对每轮记录任务、动作、参数、结果与退出原因。记录应足以回答“为什么这次没完成”，而不是只有“执行失败”。

### 5.4 阶段四：按需求增加增强能力

| 观察到的缺口 | 可以考虑的能力 |
| --- | --- |
| 无法找到项目资料 | 检索或搜索工具 |
| 多次会话无法延续进度 | 任务笔记和记忆 |
| 历史太长，输入重点不清 | 上下文预算、筛选、摘要 |
| 不同阶段相互干扰 | 更明确的角色与数据契约 |
| 用户无法了解等待状态 | 真实后端事件或任务进度 |

新增机制之后，重新跑相同样例，检查它是否解决了原问题。

### 5.5 阶段五：再完善界面与交付

流程稳定后，把结构化数据映射到页面。结果页面应保留来源、执行状态和必要的失败说明，避免把兜底内容显示成真实完成结果。

界面只是最后一层。API、数据契约和结果质量没有稳定时，先美化页面会使问题更难定位。

## 6. 怎样设计验收样例

建议至少包含以下几类，这是实践模板：

| 类型 | 示例 | 需要观察 |
| --- | --- | --- |
| 正常路径 | 合法输入且资料充足 | 是否完成目标，来源是否对应 |
| 缺少资料 | 目标事实不在资料里 | 是否说明无法确认 |
| 格式边界 | 空输入、缺字段 | 是否在合适层给出错误 |
| 工具失败 | 路径不存在或查询失败 | 是否保留原因并合理终止 |
| 预算边界 | 步数或时间达到上限 | 是否报告未完成状态 |
| 连续运行 | 两次独立用户任务 | 是否混入上次状态 |

每个样例先写期望行为，再运行程序。单纯截一张“看起来回答不错”的图，无法检验这些边界。

## 7. README 应写到什么程度

README 是让其他人在新环境中复现的入口，应覆盖：

1. 目标与使用场景。
2. 输入输出示例。
3. 模块结构与主调用链。
4. Python、依赖和必要外部服务。
5. 配置字段与优先级。
6. 启动命令及工作目录。
7. 验证方式和已知限制。

把“实现了什么”和“计划做什么”分别写清。若使用了模拟数据或备用结果，也应明确标记，避免读者误以为所有工具都已接通。

## 8. 怎样阅读社区共创项目

[Co-creation-projects/README.md](../../Co-creation-projects/README.md) 是社区入口。目录内项目来自不同作者，有独立依赖、入口和业务目标。

### 8.1 第一轮只找项目身份

先看 README：解决什么问题，调用什么模型，是否有演示、依赖与启动命令。再看 requirements/pyproject/package.json，确认它实际使用的框架。

不要因为放在 Hello-Agents 仓库里，就推断所有项目一定使用相同的 hello_agents API 或版本。

### 8.2 第二轮追踪一条最短主路径

从 main.py、Notebook 或 HTTP 入口进入，找到一次模型请求和一次真实工具操作，观察数据如何返回。

先回答“一个请求怎么跑完”，再研究记忆、评估和高级编排。否则容易被目录数量和角色名称分散注意力。

### 8.3 第三轮检查状态与效果

核对用户隔离、对象复用、文件路径、历史保存、取消与兜底。查看报告生成的数据来自真实运行还是预置样例。

本次详细文档没有逐个审查全部社区项目，因此这里只提供阅读方法，不对每个项目的可运行性或质量作整体保证。

## 9. 原始说明之间的细微差异

社区目录 README 的结构示例把 main.ipynb 标为必需；第十六章正文则允许 Notebook 或 Python 脚本。准备投稿时，应以实际项目的贡献约定和评审要求进一步核对，不能机械地认定两份说明完全一致。

命名约定为 `{GitHub用户名}-{项目名称}`，并提供 README 与依赖说明。提交、推送和创建 PR 是独立协作动作；本次只编写学习文档，没有执行这些操作。

## 10. 将学习成果转为能力的判断标准

能够从一个真实目标出发，选择必要组件，写出数据契约，追踪完整调用链，验证正常与失败路径，并让其他人按文档复现，就是毕业设计最重要的成果。

遇到新技术时，也可以沿同一结构判断它放在哪一层、补足什么缺口、如何证明效果，而不必重新建立一套互不相连的概念。

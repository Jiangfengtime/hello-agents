## 1. 本部分要建立什么认识

这部分解决三个层次的问题：第一，Agent 为什么不只是聊天模型；第二，在 LLM 出现之前，程序怎样“表现得像在交流”；第三，LLM 的文本表示和生成机制如何影响 Agent 的设计。

学完后，应能区分模型参数、提示词、程序控制逻辑和外部环境。它们共同影响结果，但修改的位置和验证方式不同。

## 2. 第一章：从一次模型调用到完整行动循环

源码入口：[FirstAgentTest.py](../../code/chapter1/FirstAgentTest.py)。

### 2.1 用户需求为什么需要多个步骤

示例任务是查询北京天气，再根据天气推荐景点。最终推荐依赖实时天气，而实时天气不应仅靠模型训练时的知识回答。

把任务展开，就是：

```text
理解目标：天气 + 适合的景点
→ 查询天气
→ 取得实际天气结果
→ 根据城市和天气搜索景点
→ 汇总推荐
```

这里天气结果是下一次搜索的输入。因此，一开始就让模型同时写出所有结果，会跳过对真实环境的观察。

### 2.2 四个模块怎样合作

| 模块 | 当前源码 | 职责 |
| --- | --- | --- |
| 行为约定 | `AGENT_SYSTEM_PROMPT` | 告诉模型可用工具和输出格式 |
| 模型连接 | `OpenAICompatibleClient` | 把 system/user 消息发给服务 |
| 环境工具 | `get_weather`、`get_attraction` | 访问天气与搜索服务 |
| 控制器 | 文件末尾的 `for i in range(5)` | 解析动作、执行工具、记录结果、终止 |

模型不知道 Python 运行时里的函数对象。提示词中的工具介绍让它生成动作文本，控制器再把动作文本映射到真实函数。

### 2.3 消息不是把所有内容随意拼在一起

`generate(prompt, system_prompt)` 构造两条消息：

```python
messages = [
    {"role": "system", "content": system_prompt},
    {"role": "user", "content": prompt},
]
```

system 消息保存角色、工具与格式约定；user 消息携带由 `prompt_history` 拼接的任务执行记录。

这意味着当前实现把多个步骤的历史压进同一条 user 文本中。历史虽然存在，但没有逐项转换成原生 assistant/tool 消息。理解后续框架时，要分别观察“历史包含什么”和“历史用什么消息结构传输”。

### 2.4 天气工具怎样执行

`get_weather(city)` 构造 `https://wttr.in/{city}?format=j1`，请求 JSON，检查 HTTP 状态，再读取：

```text
current_condition[0]
├── weatherDesc[0].value  天气描述
└── temp_C               摄氏温度
```

函数最终把结构化数据格式化成自然语言字符串，交给模型阅读。模型看到的是工具整理后的内容，不是 HTTP 响应对象。

源码区分网络请求异常和字段解析异常，并返回错误字符串。控制循环不会因为字符串以“错误”开头就自动终止；它仍可能把错误当 Observation 传回模型。

当前 `requests.get()` 未显式配置 timeout。这是源码行为，需要与模型客户端超时分开理解。

### 2.5 景点工具怎样执行

`get_attraction(city, weather)` 读取 `TAVILY_API_KEY`，把城市和天气拼成检索 query，调用 Tavily。

返回值有三条路径：

1. 搜索结果带 `answer`，直接使用服务给出的综合回答。
2. 没有综合回答，拼接 `results` 中的标题与内容。
3. 没有结果或发生异常，返回说明文字。

因此，此例里可能同时存在两个生成层：搜索服务提供的答案，以及最后由 Agent 模型生成的推荐。调试事实来源时，应观察景点工具到底返回了什么。

### 2.6 动作文本如何变成函数调用

以下是格式示意：

```text
Action: get_weather(city="北京")
```

程序先解析 `Action:` 后面的文本，再用正则提取函数名和参数：

```python
kwargs = dict(re.findall(r'(\w+)="([^"]*)"', args_str))
observation = available_tools[tool_name](**kwargs)
```

`kwargs` 是普通字典，例如 `{"city": "北京"}`。`**kwargs` 会展开成 Python 关键字参数，相当于 `get_weather(city="北京")`。

这个解析器主要匹配双引号包裹的字符串参数，不能据此推断它支持任意 JSON、列表、嵌套对象或复杂转义。后续工具框架引入参数 schema，正是为了减少这种文本解析歧义。

### 2.7 反馈闭环怎样形成

假设工具得到“北京下雨”，控制器会加入：

```text
Observation: 北京当前天气：Rain，气温18摄氏度
```

下一轮 `full_prompt = "\n".join(prompt_history)` 时，这条观察进入模型输入。模型可以据此改为搜索室内景点。

这就是反馈闭环：外部结果改变下一步动作。决定下一轮行为的材料来自运行中的工具结果，而不只是最初的用户问题。

### 2.8 状态与结束条件

`prompt_history` 是文件级列表，运行过程中不断追加模型输出与观察结果。最多执行五轮；模型输出 `Finish[...]` 时提前退出。

源码还尝试截断多余 Thought-Action 对，说明即使提示词要求每轮只执行一步，程序仍需处理模型偏离格式的情况。

当前脚本没有完整的 `__main__` 包裹，配置和控制循环位于模块顶层。导入该文件也可能触发初始化和执行，不适合直接作为无副作用工具库引用。

### 2.9 运行前特别注意配置覆盖

源码存在 `YOUR_API_KEY`、`YOUR_BASE_URL` 等占位符，并直接把 `os.environ['TAVILY_API_KEY']` 设成占位值。即使终端提前设置了真实 Tavily key，该赋值也会覆盖进程中的值。

所以第一章适合阅读完整闭环；若要快速验证模型连接，第四章独立客户端的配置方式更清晰。这里记录现状，未修改脚本。

### 2.10 建议的观察练习

先不运行外部服务，只跟踪变量变化：用户问题如何进入 `prompt_history`；模型动作怎样变成 `tool_name / kwargs`；工具结果何时回填；Finish 何时被识别。

能够手写一次“查询天气 → 搜索景点 → 结束”的变量变化表，才说明已经理解 Agent 的执行机制。

### 2.11 环境反馈是否属于 Agent Loop

属于完整闭环，但环境通常画在 Agent 本体之外。两个说法描述的范围不同：**Agent 内部完成感知、决策、执行；Agent 与环境共同构成行动—反馈闭环。**

```text
用户提出任务 → 感知输入 → 根据目标和当前信息决策
                         ↓
接收新 Observation ← 环境返回结果 ← 执行动作
         └────────→ 下一轮决策，或结束
```

查询天气是一次动作，天气接口返回的数据是环境反馈；把返回数据组织成下一轮可读的 Observation 是应用程序的工作。反馈也可能是超时、空结果或错误，而非成功信息。模型不能仅凭“我已调用工具”就知道真实结果。

设计任务时可以用 PEAS 检查四件事：Performance（什么算成功）、Environment（在哪里行动）、Actuators（能执行什么动作）、Sensors（能接收什么信息）。旅行助手的成功标准可以是“推荐符合当天天气且有来源的景点”，环境是天气/搜索服务，动作是 API 调用，感知是用户输入和工具返回值。环境信息是否完整、是否随时间变化，决定了是否需要再次查询。

### 2.12 `.py` 和 Notebook 的配置不能混看

本地两个版本当前使用不同入口：

| 入口 | 当前读取方式 | 排查重点 |
| --- | --- | --- |
| [FirstAgentTest.py](../../code/chapter1/FirstAgentTest.py) | 顶层占位配置，并直接给 `os.environ['TAVILY_API_KEY']` 赋值 | 脚本赋值会覆盖已有环境变量 |
| [FirstAgentTest.ipynb](../../code/chapter1/FirstAgentTest.ipynb) | 调用 `load_dotenv()`，读取 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`MODEL_ID`、`TAVILY_API_KEY` | 核对内核、加载路径和变量名；修改后重新运行配置单元格 |

它们使用的是服务商分别签发的密钥：模型服务密钥用于 LLM，Tavily 密钥用于搜索。变量名只是程序约定；两个 Tavily 配置位置并不代表需要两种不同密钥。

## 3. 第二章：规则系统为什么能对话，又为什么有限

源码：[ELIZA.py](../../code/chapter2/ELIZA.py)。

### 3.1 核心逻辑是匹配规则

`rules` 是按插入顺序遍历的字典：正则表达式对应若干回复模板。`respond()` 取第一个匹配项，提取捕获组，转换代词，再随机选模板输出。

```text
用户文本 → 正则匹配 → 提取片段 → 人称转换 → 填入模板
```

例如输入 `I need help`，`r'I need (.*)'` 捕获 `help`，再填入 `Why do you need {0}?` 等模板。

### 3.2 代词转换在做什么

`swap_pronouns()` 把文本小写并按空格分词，然后查 `pronoun_swap` 字典：`my → your`、`me → you`。

这是局部词替换，没有依靠上下文进行完整语法分析。它能让模板更像自然对话，但也可能处理不了标点、复杂句式和词义差别。

### 3.3 为什么通配规则要放在后面

`r'.*'` 几乎能匹配任何输入。如果把它放在最前面，前面的特定意图就永远没有机会被选中。

这一点可迁移到 Agent 工程：规则顺序、路由优先级、异常分支位置都可能决定实际走哪条路径。

### 3.4 与第一章对比

| 维度 | ELIZA 示例 | 第一章 Agent |
| --- | --- | --- |
| 响应产生 | 正则与模板 | 模型生成 |
| 行为选择 | 预先写好的匹配顺序 | 模型选择动作，程序负责执行 |
| 外部信息 | 当前脚本没有查询工具 | 天气和搜索服务 |
| 历史状态 | respond 本身无跨轮记忆 | prompt_history 累计任务轨迹 |
| 主要失败方式 | 不匹配语义或模板不自然 | 生成、解析、工具、网络等多层失败 |

这不是说规则失去了价值。格式检查、参数校验、结束条件仍适合交给确定性程序，语言理解和开放任务规划则可以交给模型。

### 3.5 符号主义、联结主义与神经符号主义

| 路线 | 知识主要怎样表示 | 怎样得到结论 | 典型例子 |
| --- | --- | --- | --- |
| 符号主义 | 显式事实、概念、逻辑规则 | 按可描述的规则推理、搜索 | 专家系统、规则推理器 |
| 联结主义 | 神经网络的连接权重和分布式表示 | 从训练数据优化参数，再进行数值计算 | 神经网络语言模型 |
| 神经符号主义 | 神经表示与显式符号知识结合 | 神经模块与符号推理/约束相互配合 | 图像识别得到事实，再由规则引擎推理可行动作 |

专家系统通常属于符号主义。例如事实是“下雨”，规则是“下雨时优先推荐室内景点”，推理器按规则得出推荐方向。规则由谁维护、冲突怎样解决，都是系统设计的一部分。

联结主义是一种研究思路，神经网络是其主要实现。“自下而上”指从样本和局部连接的参数调整中形成整体能力，而不是先把每一条高层知识写成规则。它借鉴神经元连接的思想，但人工神经网络并不是生物大脑的精确复制。亚符号表示强调知识分布在数值向量和权重里，单个数值通常不对应一条可直接读出的规则；联结主义通常采用这种表示，但两者并非严格同义词。

区分亚符号与神经符号时，看有没有**承担知识表达或推理职责的显式符号机制**。神经网络识别照片中有桌子和杯子，再由规则系统依据“杯子在桌子上”“拿走桌子会失去支撑”等关系推导动作约束，是直观的神经符号组合。LLM 调一次天气 API、程序使用 `if` 分支或 JSON 格式，本身不足以证明它是神经符号系统；这些也可能只是普通软件控制流程。神经符号主义包含多种耦合方式，上述例子是理解入口，不是唯一结构。

## 4. 第三章：语言模型基础怎样影响 Agent

### 4.1 N-gram：语言建模是条件概率问题

[N_gram.py](../../code/chapter3/N_gram.py) 统计语料中单词与相邻词对的次数，以近似计算：

```text
P(datawhale agent learns)
≈ P(datawhale) × P(agent | datawhale) × P(learns | agent)
```

脚本中语料只有六个词，重点是理解条件概率分解。N-gram 用有限的前文估计下一个词；更复杂的语言模型通过参数化网络表示更丰富的上下文关系。

对 Agent 的启示：模型输出是基于输入的生成结果，不是执行凭证。它说“我已调用搜索”，仍需工具日志证明搜索真实发生。

### 4.2 BPE：为什么一个词不一定是一个 Token

[BPE.py](../../code/chapter3/BPE.py) 从按字符拆开的词表开始：

```python
vocab = {"h u g </w>": 1, "p u g </w>": 1}  # 这里只展示部分词条
```

流程是统计相邻符号对 → 找最高频 pair → 合并 → 再次统计。`freq` 用作计数权重，`</w>` 标识词尾。

`merge_vocab()` 使用边界正则替换完整符号对，避免把一个符号内部的字符串误当成待合并单元。

这一示例演示合并规则的学习过程，没有实现一个与某个商用模型完全相同的 tokenizer。真实 token 数应使用目标模型对应的编码器计算，不能把 Python `len(text)` 当作准确 token 数。

对 Agent 的影响是：提示词、历史、工具输出都占上下文空间；内容越多，输入成本和处理压力通常也会增加。

### 4.3 Embedding：把符号变成数值表示

[Word_Embedding.py](../../code/chapter3/Word_Embedding.py) 使用人工指定的二维向量演示：

```text
king - man + woman
```

再计算结果与 queen 的余弦相似度：

```text
cos(a, b) = 点积(a, b) / (向量长度(a) × 向量长度(b))
```

脚本没有训练词向量；这些数值用于教学。它表达的是“可通过向量空间中的距离或方向关系比较表示”。

后续 RAG 会把问题和文档片段映射为向量，再寻找相关内容。但“向量相似”不能直接等同于“论断正确”，仍需检查原始来源。

### 4.4 Transformer：输入在网络中如何流动

[Transformer.py](../../code/chapter3/Transformer.py) 实现一个教学用 encoder-decoder Transformer，包括词嵌入、位置编码、多头注意力、前馈网络与输出投影。

想系统理解各模块的职责，可读[Transformer 架构原理详解](08-Transformer架构原理详解.md)；想看原始架构的一条具体数据流，可读[用翻译例子走完 Transformer 的完整流程](07-Transformer完整流程示例.md)；想理解 GPT 类模型的生成过程，可读[Decoder-Only 架构详解](09-Decoder-Only架构详解.md)；想比较 Encoder-Only、Decoder-Only 和 Encoder–Decoder，并厘清 BERT 与 Bard 的区别，可读[Transformer 三种架构对照详解](10-Transformer三种架构对照详解.md)；想弄清下一个 Token 如何选出，可读[模型采样参数详解](11-模型采样参数详解.md)。

它的主要数据流为：

```text
src token IDs → Encoder → encoder_output
tgt token IDs + encoder_output → Decoder → 词表 logits
```

这份代码是 encoder-decoder 结构，不应直接等同于所有 decoder-only 大模型的具体实现。

### 4.5 Q、K、V 与形状变化

设批大小为 B，序列长度为 L，隐藏维度为 D，头数为 H，每头维度 d=D/H：

| 步骤 | 形状 | 含义 |
| --- | --- | --- |
| 输入表示 | `[B, L, D]` | 每个 token 有一个 D 维向量 |
| 线性投影 | `[B, L, D]` | 分别产生 Q、K、V |
| 拆头并转置 | `[B, H, L, d]` | 每个头独立计算注意力 |
| `Q @ Kᵀ` | `[B, H, L, L]` | 每个位置与各位置的关联分数 |
| softmax 后乘 V | `[B, H, L, d]` | 按权重汇总内容 |
| 合并多头 | `[B, L, D]` | 返回后续网络需要的形状 |

Q 可以理解为当前位置用来“查询”的表示，K 用来“被匹配”，V 是实际被加权汇总的内容。三者均为网络计算出的张量，不是数据库里的查询语句和记录。

`K.transpose(-2, -1)` 交换末尾两个维度，为矩阵乘法对齐；合头时使用 `contiguous().view(...)`，是因为转置后张量布局可能不满足直接 view 的要求。

### 4.6 Mask 为什么必要

源码把 padding token ID 约定为 0：`src != 0` 排除补齐位置。目标序列还使用下三角 mask，让位置 t 不读取 t 之后的目标 token。

注意力得分在被屏蔽位置填入很小的负数，softmax 后其权重接近零。这样既避免把 padding 当实际内容，也约束自回归训练中的未来信息泄漏。

### 4.7 位置编码、残差、前馈各解决什么

位置编码补充序列顺序信息；注意力将不同位置的信息混合；前馈网络对每个位置进行非线性变换；残差连接与归一化帮助信息传递和数值稳定。

理解这些组件，是为了知道模型依靠上下文处理输入。Agent 的外部记忆不在这些层里自动增长，而是由应用把检索到的信息重新放回输入。

### 4.8 从 N-gram 过渡到神经网络语言模型

语言模型的目标是估计 `P(下一个 Token | 已有上下文)`。概率链式法则允许写出整句概率的乘积；N-gram 进一步做了近似：只使用前 `n−1` 个词，而不是完整历史。

固定窗口神经网络语言模型也可以使用前 `n−1` 个词，但不再单纯查计数表。例如上下文为“今天 / 天气 / 很”，窗口大小为 3：

```text
3 个 Token ID → 查嵌入表 → 3 个 D 维向量
→ 拼接成 3D 维输入 → 神经网络隐藏层 → V 维 logits
→ Softmax → 词表 V 个候选各自的概率
```

输出是整个词表的概率分布，不是已经选好的一个词。“好”的真实标签用于计算损失，反向传播会更新隐藏层和通常可训练的嵌入表。项目中手工展示向量的示例只帮助理解表示形式，不能代替这个训练过程。[神经网络概率语言模型原始论文](https://www.jmlr.org/papers/v3/bengio03a.html)

RNN 将历史信息压缩进递归更新的隐藏状态，因此不必用固定宽度的向量拼接，但时间步之间存在串行依赖。Transformer 使用注意力在可见上下文中混合信息；它仍受上下文窗口及计算资源限制，不等于能无条件读取无限历史。

### 4.9 分词、预训练、微调、提示各改变什么

BPE 的训练阶段从语料中学习合并规则；推理阶段使用已有分词器及词表，不会每读一条用户输入就重新训练 BPE。中文汉字、英文单词、空格与标点如何分成 Token 取决于分词器，不能用字数直接替代 Token 数。

| 阶段 | 输入/目标 | 是否通常更新模型权重 |
| --- | --- | --- |
| 预训练 | 大量文本，学习语言统计与表示；自回归模型常预测下一 Token | 是 |
| 监督微调（SFT） | 指令—回答等示范，学习任务响应形式 | 是；可全量或参数高效微调 |
| 偏好优化/强化学习 | 偏好对或奖励，调整输出行为 | 是，但具体优化目标不同 |
| 提示、Few-shot、RAG | 把指令、示范或检索证据放入本次上下文 | 常规推理中否 |
| Agent 记忆写入 | 将事实/经历存入外部数据库，之后检索 | 常规应用中否 |

Zero-shot 是不提供任务示范，Few-shot 是在提示中提供少量示范，并不自动执行参数训练。模型规模、训练数据和计算预算共同影响表现；“规模更大”不能替代任务评估，也不会保证事实正确。选模型需要在真实任务上比较质量、延迟、成本、上下文需求与工具调用可靠性。

## 1. 为什么从范式讲到框架

第一部分已经能把模型和工具连起来。现在要解决的问题是：面对不同任务，应选择怎样的执行策略；当这些策略重复出现时，哪些部分可以抽象复用。

这部分形成四层认识：经典范式决定控制流程；低代码平台表达工作流；现成框架提供协作与状态机制；自建框架统一模型、消息、工具和 Agent 接口。

## 2. 第四章：把三种控制策略读透

### 2.1 ReAct 的关键不在于打印了 Thought

关于 ReAct 与原生 Function Calling 的关系，以及 Finish 和无工具调用两种停止条件，见[专题对照](12-ReAct与FunctionCalling及AgentLoop的关系.md)。

[ReAct.py](../../code/chapter4/ReAct.py) 每轮根据问题、工具描述和已有 Observation 构造提示词，再决定继续行动还是结束。

真正构成闭环的是：

```text
生成动作 → 程序解析 → 工具执行 → 取得观察 → 进入下一轮输入
```

`Thought` 是输出文本的一部分。程序读取文本中的规划说明，并不意味着这些文字是模型内部计算过程的完整或可验证记录。判断行动是否发生，要看 `_parse_action()` 之后的函数调用。

### 2.2 从入口追到返回值

入口创建 LLM、ToolExecutor，注册名为 `Search` 的函数，随后调用 `agent.run(question)`。每次 run：

1. 清空 `self.history`，初始化步数。
2. 把注册表的描述放进模板，告诉模型能用哪些工具。
3. 调用 `think()`，得到完整响应字符串。
4. 用 `_parse_output()` 提取 Thought 与 Action。
5. Action 以 Finish 开头则提取答案并返回。
6. 否则解析工具名和输入，查找函数，执行并追加 Observation。

`history` 保存 Action 和 Observation，没有把全部 Thought 都存回去。这是具体实现的上下文选择，而不是 ReAct 必须保存哪些文本的普遍规定。

### 2.3 ToolExecutor 的字典究竟保存了什么

[tools.py](../../code/chapter4/tools.py) 的结构近似：

```python
tools = {
    "Search": {
        "description": "工具说明",
        "func": search,
    }
}
```

`func` 是 Python 函数对象。工具描述给模型阅读；函数对象给程序调用。工具注册完成，并不代表函数已执行。

`getTool()` 通过精确名称查找，因此 `Search` 与 `search` 是不同的字典键。模型输出与注册名不一致时，程序会得到“未找到工具”的观察结果。

搜索函数又有自己的返回优先级：直接答案列表 → 单条直接答案 → 知识图谱描述 → 前几个搜索摘要 → 无结果说明。调试时不能只查看搜索 API 是否返回 200，还要看选中了哪条解析分支。

### 2.4 为什么解析器是薄弱环节

`_parse_action()` 主要匹配 `工具名[输入]`。若模型额外输出解释、多个动作或格式不完整，正则可能解析失败或得到不期望的参数。

当前实现没有独立的动作对象和严格 schema，所以“模型回答合理”与“程序能执行”之间还有格式约束。学习时可以构造几个响应字符串，逐步观察正则结果，无需真实调用模型。

### 2.5 步数上限怎样理解

`max_steps=5` 限制的是控制循环，成功退出仍需识别 Finish。若前五轮都用于调用工具，当前实现不会再自动追加第六轮总结，最终可能返回 None。

这与第七章 MySimpleAgent 达到工具迭代上限后再调用一次模型的策略不同。限制名称类似，也必须看方法体。

### 2.6 Plan-and-Solve 为什么要分 Planner 和 Executor

[Plan_and_solve.py](../../code/chapter4/Plan_and_solve.py) 让 Planner 输出子任务列表，Executor 再逐步执行。

对“周一卖 15 个、周二翻倍、周三少 5 个、求总数”这样的题目，示意计划可为：计算周二 → 计算周三 → 求三天总数。每一步带入之前的结果，减少一次生成中遗漏步骤的机会。

两者虽然使用同一个模型客户端，但提示词职责不同：Planner 负责拆分和顺序；Executor 专注当前子任务。

### 2.7 `ast.literal_eval()` 为什么出现在计划解析里

模型被要求在 Python 代码块中输出列表。程序先从代码块提取文本，再用 `ast.literal_eval()` 解释成 Python 字面量。

这能解析列表和字符串等数据，不会像任意 `eval()` 那样直接执行一般 Python 表达式。但是解析成功后，源码只检查是否为 list，没有进一步保证每项都是有效任务字符串，也没有验证计划确实完整。

这里至少有三层验证：文本格式正确 → 数据结构正确 → 业务计划正确。前两层可用程序约束，第三层仍需任务评估。

### 2.8 执行器实际怎样使用历史

Executor 在每轮提示词中传入：原问题、完整计划、已执行步骤与结果、当前步骤。每完成一步，就把结果追加到局部 history 字符串。

它没有重新规划逻辑；即使中间发现原计划不合适，也不会自动更新剩余步骤。是否增加重规划，是后续工程设计选择，当前代码尚未实现。

最后一步结果作为 `Executor.execute()` 的返回值，外层 `PlanAndSolveAgent.run()` 当前只打印该值。外部脚本若要接收结果，需要留意这一接口差别。

### 2.9 Reflection 的状态为何单独封装

[Reflection.py](../../code/chapter4/Reflection.py) 的 Memory 保存 `execution` 和 `reflection` 两类记录。通过类型标记，可以区分“上一版代码”和“评审意见”，而不是把所有文本混成无结构字符串。

每轮取最近一次 execution 给评审提示词，再把反馈与原代码交给修订提示词。这里只需要最新代码和本次反馈；完整轨迹虽然被记录，但不能由此推断每轮都使用全部轨迹。

`Memory` 随 Agent 对象创建，当前 run 开头没有重置所有记录。复用对象时，记录列表会继续累积，这与 ReAct 每轮任务清空 history 不同。

### 2.10 评审停止不代表程序通过测试

反思提示要求返回 JSON，包含布尔字段 `needs_improvement` 和非空字符串 `feedback`。只有 `needs_improvement` 严格为 `false` 时才提前结束；“不能认为无需改进”等正文不会影响判断。非空但格式不合法的反馈继续进入优化，空反思响应报错。达到迭代上限时返回最新代码，不代表最后一版已经评审通过，也没有执行自动化正确性测试。

例如素数函数可能看起来复杂度更好，却遗漏 `n < 2` 的情况。要验证正确性，还需实际输入和期望输出；Reflection 可以提出改进，但证据要来自可检验结果。

### 2.11 三种策略如何选择

| 任务特征 | 可优先观察的范式 | 需要额外控制 |
| --- | --- | --- |
| 后续步骤依赖外部反馈 | ReAct | 工具错误、循环上限、动作格式 |
| 子任务相对清晰且顺序明确 | Plan-and-Solve | 计划完整性、中间结果、是否重规划 |
| 已有初稿，需要迭代改善 | Reflection | 评价标准、修订是否退步、真实测试 |

实际应用可以组合这些策略，例如先规划研究主题，再对每个子任务检索，最后评审报告。组合应解决具体缺口，不必为了覆盖名称而增加循环。

## 3. 第五章：低代码平台把程序的哪部分可视化

源码材料位于 [chapter5](../../code/chapter5/)，包括 Coze 压缩包、Dify YAML、n8n JSON 和 FastGPT JSON。它们主要是平台导出材料，不能当作普通 Python 脚本启动。

### 3.1 用程序思维阅读流程图

一个典型工作流可示意为：

```text
输入节点 → 数据整理 → 模型节点 → 条件分支 → 工具/知识检索 → 输出节点
```

节点对应一次处理，连线对应执行依赖，节点变量对应函数参数或状态字段。阅读时要找：输入从哪里来、每步输出叫什么、下一步如何引用、哪条分支处理失败。

### 3.2 工作流与自主动作选择的边界

固定流程由开发者预先决定执行顺序；Agent 节点可能让模型在限定工具中选择动作。同一应用可以同时包含两者。

因此判断是否有动态决策，应看模型输出是否真的影响后续执行路径，而不是看界面上是否叫“Agent”。

### 3.3 导入材料时怎样验证

先读目标平台及导出文件中的节点配置，再核对模型连接、凭证引用、变量名和知识库标识。导出文件含有工作流定义，并不保证接收环境已经拥有相同插件、数据和密钥。

本次没有把这些导出材料导入平台执行，平台适配和最终效果应单独验证。

## 4. 第六章：四种框架示例分别在展示什么

### 4.1 AutoGen：轮流协作与终止条件

[autogen_software_team.py](../../code/chapter6/AutoGenDemo/autogen_software_team.py) 创建产品经理、工程师、代码审查员和用户代理，再放入 RoundRobinGroupChat。

```text
任务 → 产品经理分析 → 工程师生成 → 审查员反馈 → 用户代理
                                      ↑             ↓
                                      └──后续轮次───┘
```

`participants` 顺序决定轮转顺序，`TextMentionTermination("TERMINATE")` 和 `max_turns=20` 限制结束条件，Console 消费团队的运行事件流。

这里的 `UserProxyAgent` 是真人反馈入口，不是自动测试代码的模型角色。源码只设置了名称和描述，没有为它设置模型客户端、自动执行工具或自定义输入函数；默认人类输入路径可能等待控制台输入。描述中的“测试”表达人的职责，不能让程序自动测试。需要真人反馈或测试运行结果才能证明代码可用。[AutoGen 人类参与文档](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/human-in-the-loop.html)

### 4.2 AgentScope：可见消息与游戏规则

[main_cn.py](../../code/chapter6/AgentScopeDemo/main_cn.py) 用狼人杀展示多角色推理。控制器管理玩家、存活状态、阵营和回合，而角色 Agent 生成发言或选择。

MsgHub 组织某组参与者的消息交互；sequential_pipeline 表达顺序执行；fanout_pipeline 用于收集多个参与者输出。具体调度语义仍以该案例依赖版本为准。

学习重点是“谁能看到什么”。夜间阵营讨论与白天全员发言的信息范围不同。如果把所有私有信息放进每个角色输入，游戏机制就会失效，即使文本依然流畅。

### 4.3 CAMEL：角色扮演式任务协作

[DigitalBookWriting.py](../../code/chapter6/CAMEL/DigitalBookWriting.py) 设置作家和心理学家，通过 RolePlaying 逐轮交互：`init_chat()` 初始化，`step(input_msg)` 生成双方响应，再把 assistant 响应作为下一轮输入。

最多执行 30 轮，或在 user 角色文本中出现 `CAMEL_TASK_DONE` 后结束。此处 user 角色是协作中的模型角色，并非每轮都由真实用户输入。

源码主要打印交流内容，没有单独展示把完成书稿保存为电子书文件的导出过程。任务提示要求的字数也不能代替实际产物长度验证。

配置读取 `LLM_MODEL`，与很多章节使用的 `LLM_MODEL_ID` 不同；运行时要按此文件核对。

### 4.4 LangGraph：用状态和边描述执行

[Dialogue_System.py](../../code/chapter6/Langgraph/Dialogue_System.py) 定义 SearchState：

| 字段 | 用途 |
| --- | --- |
| `messages` | 消息列表，带 add_messages 合并标记 |
| `user_query` | 需求理解相关内容 |
| `search_query` | 发给搜索服务的关键词 |
| `search_results` | 搜索得到的资料 |
| `final_answer` | 最终回答 |
| `step` | 当前阶段标记 |

图中固定边为 START → understand → search → answer → END。节点返回状态更新，图运行时协调流转。

InMemorySaver 提供进程内检查点；调用配置的 `thread_id` 用来标识运行线程/会话。当前主循环为不同搜索创建递增的 session ID，不能直接认为它天然把每次新查询串为同一长会话。

### 4.5 从四个案例抽取共同问题

框架名称不同，仍要回答相同的问题：谁安排执行顺序，谁拥有状态，消息被谁看到，什么触发结束，出错怎样恢复。

理解这些问题之后，再查框架 API 会更有方向。当前案例分别采用不同依赖声明，不应把某个新版本框架文档中的接口直接套到历史代码上。

## 5. 第七章：怎样抽象自己的 Agent 框架

### 5.1 为什么需要统一接口

前几章重复出现模型初始化、消息拼装、历史保存、工具查询和输出解析。将这些功能抽象后，业务代码可以专注任务，而不必每次重写连接和注册逻辑。

但抽象要区分责任：模型客户端处理“怎样调用”；Agent 处理“什么时候调用”；工具处理“实际做什么”；Registry 处理“按什么名称找到工具”。

第七章正文讲解完整框架设计；当前配套代码使用外部 `hello_agents` 包，再继承并重写部分行为。

### 5.2 MyLLM 的参数与初始化分支

[my_llm.py](../../code/chapter7/my_llm.py) 提供 model、api_key、base_url、provider 以及 kwargs。

当 provider 为 modelscope 时，自行设置客户端；模型选择顺序为显式 model → `LLM_MODEL_ID` → 代码默认值，密钥选择为显式 api_key → `MODELSCOPE_API_KEY`。其他 provider 交给父类。

注意当前 ModelScope 分支的 base_url 使用显式参数或代码默认值，没有在这个赋值表达式中读取 `LLM_BASE_URL`。不能将其他章节的配置优先级直接套过来。

该分支不调用父类初始化，因此还依赖本地设置的属性与父类继承方法兼容。若升级依赖后缺少属性，应查看实际父类方法访问哪些字段。

### 5.3 MySimpleAgent 的消息组装

[my_simple_agent.py](../../code/chapter7/my_simple_agent.py) 按顺序构造：增强 system prompt → `_history` → 当前 user。增强提示词会包含工具描述和 `[TOOL_CALL:工具名:参数]` 格式。

没有工具时直接 invoke，完成后保存 user/assistant；有工具时进入 `_run_with_tools()`，每轮解析动作、执行、回填结果并继续调用。

`max_tool_iterations` 限制的是工具处理循环的轮数，一轮中可能解析并执行多个工具调用，因此它不等于工具调用总次数。达到上限后，当前实现还会额外调用模型生成最终回应；这一回应不会再次经过工具解析执行流程，即使里面还有工具标记，也不能当作工具已经执行。

### 5.4 工具参数为什么需要按类型处理

当前工具参数支持 `key=value`、逗号分隔的多个参数以及直接字符串。直接字符串会按工具名映射为 query、memory search 或 input。

这种映射便于演示，但存在边界：逗号也可能属于自然语言内容；`value` 默认仍是字符串；嵌套 JSON 无法按普通 split 正确解析。业务工具应根据自己的参数 schema 做类型转换和校验。

计算器分支通过 registry 执行，其他分支先取工具再调用 `tool.run(param_dict)`。追踪调用时要区分这两条路径。

### 5.5 流式方法为何必须单独阅读

`stream_run()` 用 yield 逐段返回文本，只有消费生成器到后续位置时，保存历史的语句才会执行。若调用方提前停止迭代，不能假设完整响应已经写入 history。

而且流式方法没有 `_run_with_tools()` 的闭环。同步回答支持某能力，不代表流式接口也已经支持。

### 5.6 自定义计算器的 AST 路径

[my_calculator_tool.py](../../code/chapter7/my_calculator_tool.py) 将表达式解析为 AST，递归处理常量、二元运算、函数调用和名称。

```text
"(2 + 3) * 4"
→ 解析树：乘法(加法(2, 3), 4)
→ 递归计算左右节点
→ 从 operators 表取运算函数
→ 返回 "20"
```

它只实现部分 AST 节点和运算，例如没有显式处理一元负号和幂运算；某些未支持节点也未显式抛异常。界面声明的“计算器”能力仍需与具体分支匹配。

### 5.7 MyReActAgent 的双层历史

[my_react_agent.py](../../code/chapter7/my_react_agent.py) 的 current_history 用于本次推理，每次 run 清空；基类消息历史在完成时追加，但本方法没有把它全部放进提示词。

这说明状态至少有两个层次：一次任务内的执行轨迹，以及对象保存的聊天消息。哪一层进入本次模型调用，要看组装提示词的代码。

### 5.8 格式验证、执行权限与成功证据是三件事

工具 schema 约束参数形状，例如城市是字符串；它不保证城市存在、API 可用，也不自动授予文件写入或发送消息的权限。执行层仍要处理参数语义、异常、超时及副作用。读操作重试与写操作重试也不同：重复查询通常只是多花一次费用，重复下单则可能产生两笔订单，需要幂等机制。

Reflection 示例曾按反馈是否包含“无需改进”来停止，因此会误读“并非无需改进”；当前已改为解析显式布尔结论。达到循环上限、模型声称完成、工具返回成功和结果通过测试，应分别记录，而不是统一称为“验证通过”。

## 6. 本部分的练习与验收

| 练习 | 观察目标 |
| --- | --- |
| 手工提供一个 Finish 响应 | 验证解析器的返回值与结束条件 |
| 提供一个不存在的工具名 | 看错误进入异常还是 Observation |
| 把 `max_steps` 改小后推演 | 区分工具循环次数与最终回答机会 |
| 同一 Agent 连续运行两个问题 | 核对哪些历史被清空、哪些留下 |
| 对比同步与流式 run | 核对工具、历史和停止行为是否一致 |

这些练习可以先通过阅读和断点推演完成。真正改动代码时，每次只验证一个假设，避免同时修改模型配置、Prompt 和控制循环后无法判断改善来自哪里。
